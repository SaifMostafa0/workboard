# Workboard — PWA, offline behaviour and encrypted backups

Workboard is a local-first app, so "offline" is a product promise rather than an optimisation.
This document covers how the installable PWA is built, how the cache is versioned, and how the
optional passphrase-encrypted backup works.

## Installability

| Piece                 | Location                                             |
| --------------------- | ---------------------------------------------------- |
| Web app manifest      | `public/manifest.webmanifest`                        |
| Icons                 | `public/icons/*.png` (generated, committed)          |
| Service worker        | `public/sw.js` (post-processed at build time)        |
| Registration + update | `src/lib/serviceWorker.ts`, `useServiceWorkerUpdate` |
| Theme colour / links  | `index.html`                                         |

The manifest declares `display: standalone`, a `/` start URL and scope, a 192 px and 512 px icon,
plus a dedicated maskable icon. Icons are generated by `npm run icons`
(`scripts/generate-icons.mjs`), which writes PNGs with no image-library dependency; the output is
committed so builds stay reproducible.

Install prompts appear automatically in Chromium once the manifest, icons, and an active service
worker with a `fetch` handler are present. Safari/iOS uses "Add to Home Screen" and the
`apple-touch-icon`; it ignores the manifest icons but otherwise behaves the same.

## Cache strategy

`public/sw.js` is intentionally small and dependency-free. `scripts/build-sw.mjs` runs after
`vite build` and replaces two placeholders with:

- `self.__WORKBOARD_PRECACHE__` — the exact list of emitted files (`/`, `/index.html`, hashed JS and
  CSS, icons, manifest, favicon).
- `self.__WORKBOARD_VERSION__` — a short hash of that list, which names the caches.

| Request                        | Strategy                                                    |
| ------------------------------ | ----------------------------------------------------------- |
| Navigations (`mode: navigate`) | Network-first; fall back to the cached `/index.html` shell  |
| Same-origin JS/CSS/font/image  | Stale-while-revalidate (serve cache, refresh in background) |
| Everything else                | Network-only — Workboard makes no third-party requests      |
| `sw.js` itself                 | Never intercepted                                           |

Two caches are used: `workboard-precache-<version>` and `workboard-runtime-<version>`. Activating a
new worker deletes every cache whose name does not match the current build version, so old hashed
assets do not accumulate. Cache lookups pass `ignoreVary: true`: Vite preview (and many static
hosts) serve assets with `Vary: Origin`, while module scripts are CORS requests carrying an `Origin`
header — a plain `cache.match` would miss the entries written by `cache.addAll` and break offline
startup.

### SPA deep links

Every route is handled by the React Router data router. Offline, a navigation to `/tasks?status=todo`
is served from the precached `/index.html`, and the router renders the same route on load. The host
must therefore rewrite unknown paths to `/index.html` (Vite preview and Netlify/Vercel SPA presets do
this by default; plain static hosts need a rewrite rule). This is the same requirement the app has
without the service worker — the worker only makes it work offline.

## Update flow

`registerServiceWorker()` is called once by the layout through `useServiceWorkerUpdate()`.

1. On first visit the worker installs and precaches the shell, then activates. No prompt is shown.
2. On later visits, if a new worker installs while a controller exists, it stays in `waiting` and
   the UI shows a bottom-right banner: **"A new version of Workboard is available."**
3. "Reload to update" posts `SKIP_WAITING`; `controllerchange` then reloads the page once.
4. "Later" dismisses the banner for the session. The waiting worker stays ready.
5. Long-lived tabs call `registration.update()` hourly so a deploy is noticed without a reload.

Reloading is deliberately user-initiated: a silent swap can discard unsaved form state. Registration
is skipped in development (`import.meta.env.DEV`) so HMR never fights a precache.

## Verifying it locally

```bash
npm run build      # tsc + vite build + build-sw.mjs
npm run preview    # serve dist/
```

- Check DevTools → Application → Service Workers: `sw.js` should be activated.
- Application → Manifest: name, icons, and installability warnings should be clean.
- Switch DevTools to Offline, reload, then open a deep link such as `/tasks?status=todo`.
- Run Lighthouse (Chrome) against the preview URL; the PWA/installability audit should pass. This
  is a manual check in this repo because the CI Lighthouse job (see `docs/performance.md`) targets
  core performance metrics, not the installability category.

The manifest/worker/offline checks above are scripted and reproducible:

```bash
npm run build && npm run pwa:check
```

`scripts/check-pwa.mjs` starts `vite preview`, verifies the worker, precache, manifest and icons,
then stops the server and asserts that a fresh navigation and a deep link still render the shell
(the response must come `fromServiceWorker()`). It is not part of `npm run ci` because it needs a
real browser and a fresh production build.

## Encrypted backups

JSON export is plain text by design (inspectable, diffable, importable everywhere). For off-machine
copies, Settings → **Encrypted Backup** produces a passphrase-protected envelope implemented in
`src/lib/backup.ts`.

### Format

```json
{
  "format": "workboard-encrypted-backup",
  "version": 1,
  "createdAt": "2026-10-28T12:00:00.000Z",
  "kdf": { "name": "PBKDF2", "hash": "SHA-256", "iterations": 310000, "salt": "base64" },
  "cipher": { "name": "AES-GCM", "iv": "base64" },
  "payload": "base64 ciphertext + GCM tag"
}
```

- **Key derivation:** PBKDF2-HMAC-SHA256, 310,000 iterations, random 16-byte salt.
- **Encryption:** AES-256-GCM with a random 12-byte IV. The GCM tag makes tampering detectable.
- **Fresh randomness:** every export uses a new salt and IV, so identical data never produces
  identical ciphertext.
- **Passphrase policy:** at least 8 characters with a letter and a number. Enforced in the UI.
- **Import:** the file picker detects the envelope and asks for the passphrase; a wrong passphrase
  or modified payload fails with "Incorrect passphrase or corrupted backup file."

### Scope and threat model

- The payload is the same export as the plain JSON backup: projects, tasks (including attachment
  **metadata**), epics, labels, saved views and settings.
- **Attachment blobs are never exported** (plain or encrypted). They live only in the local
  IndexedDB attachment store.
- It protects data at rest and in transit (e.g. emailed, synced to cloud storage) against someone
  who does not know the passphrase.
- It does not protect against a compromised device, malware, a keylogger, or a weak passphrase.
- **There is no recovery.** A lost passphrase means the backup is unrecoverable; the UI says so
  before the file is created.
- The envelope's `createdAt`, KDF parameters and sizes are visible in plaintext; the data itself is
  not.

## Known limits

- No background sync, periodic background sync, or Web Push. Reminder notifications fire while
  Workboard is open (`WB-303`); reliable delivery when the tab is closed would need push
  infrastructure, which contradicts the no-backend design.
- iOS Safari cannot use SVG manifest icons; the generated PNGs and `apple-touch-icon` cover it.
- Cache updates are per-build. If two deploys happen with an identical asset list, the version hash
  is unchanged, which is correct: the bytes are identical.

## Testing

- `src/lib/__tests__/backup.test.ts` covers the envelope shape, round-trip, wrong passphrase,
  tampering, randomness and plaintext leakage.
- `src/infrastructure/repositories/__tests__/attachmentRepository.test.ts` covers the local-only
  blob store, including quota and storage-failure injection.
- The service worker itself is exercised by the production smoke test (`npm run pwa:check`) because
  jsdom does not implement `CacheStorage` or `ServiceWorkerContainer`; the update banner state
  machine is unit-tested in `src/lib/__tests__/serviceWorker.test.ts`.
